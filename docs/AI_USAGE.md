# AI 使用与验证记录

> 交付要求第 3 项。本文件记录：用了哪些 AI 工具、AI 参与了哪些环节、以及**哪些 AI 产出被人工判定为错误或不合理并做了修正**。
> 最后一节是最重要的 —— 一份只有"AI 帮我写完了"的记录没有信息量。

---

## 1. 使用了哪些 AI 工具

| 环节 | 工具 | 用途 |
| --- | --- | --- |
| 需求拆解 | 对话式大模型（AI Coding 助手） | 把题目要求拆成可验证的验收点；对比三道题的实现成本，选定题目 11 |

**产品运行时不含大模型调用**（设计理由见 README 第 4 节）：金融复盘的关键是数字可追溯，因此所有数字、归因、偏差判定都由确定性代码产出。

## 2. AI 参与的具体环节

1. **选题决策**：给出三道题的实现成本对比与理由（见 README 开头）。
2. **架构设计**：分层方案 `pit → quality → market → attribution/bias → report → guardrails`；
   每层都是纯函数，便于单测。
3. **规则设计**：9 条行为偏差规则的触发条件与阈值，以及"每条必须配反例检查"的约束。
4. **数据方案**：三条决策的结果与过程故意错配，用于演示"结果 ≠ 过程"。
5. **测试设计**：70 个用例，覆盖时点边界、四类数据异常、主链路、合规、HTTP 接口，以及扶摇适配层的字段映射与错误码；另有 14 项前端渲染冒烟检查。
6. **实现与重构**：全部源码。
7. **真实数据接入**：扶摇 API 的鉴权方式、响应信封、业务错误码与字段命名，均由 AI 依据接口返回的**实测响应**归纳；映射层的降级策略由 AI 提出初稿，经人工用真实数据逐条核对后定稿（见第 3 节第 13–17 条）。

## 3. AI 产出中被判定为错误 / 不合理并修正的部分

以下是本次开发过程中真实出现并被修正的问题。记录它们的原因是：**它们几乎都属于同一类错误——"看起来合理但语义错了"**，
这正是把 AI 产出直接当结果提交的主要风险。

| # | 问题 | 为什么是错的 | 修正 |
| --- | --- | --- | --- |
| 1 | `runBiasRules(ctx)` 里读 `ctx.facts`，但 `ctx.facts` 在调用之后才赋值 | 规则抛异常被 `try/catch` 吞掉，界面上显示为"未判定"。**如果不看输出细节，会误以为是数据不足导致的正常降级** | 在调用偏差引擎前显式 `ctx.facts = facts`；并保留异常兜底为"未判定"而非"未触发" |
| 2 | 锚定偏差规则去扫"买入理由"，而锚定措辞出现在"卖出理由"里 | 决策 C 的卖出理由含"回到成本价上方"，规则却判定未触发 —— **假阴性** | 拆出 `exitReasoning`，锚定类措辞只在卖出理由中检索 |
| 3 | 过期检查对**每一个历史数据点**逐点判断"距决策多少天" | 2023 年的收盘价必然"距决策 280 天"，产生 531 条无意义告警，把真正的降级信息淹没 | 改为只对**每个序列在决策时点可得的最新一期**做新鲜度判定；并支持按序列前缀配置阈值（日频 7 天 / 月频 PMI 40 天 / 财报 400 天） |
| 4 | 冲突样本被放在决策时点**之后** | 该点根本不在事前证据集里，时点闸门直接拦掉了，导致"冲突降级"这条演示路径**永远无法被触发** | 把冲突样本移到决策前最近一个交易日；并补测试断言 `CONFLICT` 必然出现在 `quality.issues` 中 |
| 5 | 质量体检对**整条序列**判失效（一处冲突 → 该股票所有指标不可用） | 过度降级：一条 `price` 冲突导致最大回撤、追涨、期限全部无法计算，产品可解释性反而下降 | 改为**精确到数据点**的剔除（`filterUsablePoints`），并留 `removedPoints` 记录被剔除了什么 |
| 6 | 归因 A-2 读 `decision.reasoning.matchedTerms`，但 `decision.reasoning` 是**字符串原文** | 该字段恒为 `undefined`，A-2 这条归因**从未产出**，而页面看起来一切正常 | 改为读 `ctx.reasoning.matchedTerms`（解析结果对象） |
| 7 | `sanitizeDeep()` 的返回结构与调用方约定不一致 | 合规清洗处抛 `TypeError`，整条主链路中断 | 统一约定：返回清洗后的节点，命中记录写入传入的 `acc.hits` |
| 8 | "决策依据不足"规则用 `pitEvidence.length`（原始数据点个数）做信息量指标 | 一个序列 200 个日频点会让任何决策都"信息充足"，规则形同虚设 | 改为统计**标的层面非价格类指标的种类数**（排除 `price:` / `index:` / `pmi:`），阈值 2 类 |
| 9 | 事件未按标的过滤 | 决策 A（消费股）的事前事件里混进了银行板块的研报，时间线上出现无关信息 | 按 `relatedSymbols` 过滤，`relatedSymbols` 为空视为市场级事件 |
| 10 | 故障注入接口的 `fault` 参数抛出的错误被外层统一转成 HTTP 500 | 语义上"上游不可用"应为 503，500 会让调用方误判为服务端 bug | 给注入错误加 `statusCode`，外层按其返回 |
| 11 | 时间线改造时把**行情数据点**塞进了 `events` 参数 | 渲染出「事件：undefined」与 `events[undefined]`。**程序不崩、测试全绿、页面能开**，只有肉眼看渲染文本才能发现 | 拆出 `exPostMarketEvidence` 独立参数；并新增回归断言：报告中出现 `undefined` 即失败 |
| 12 | 「时点闸门」的**文字描述方向写反**：界面提示文案、`test/pit.test.js` 的用例名、`docs/TESTING.md` 的用例表，三处都写成"时点后移 → 事前证据被移入**事后**" | 与实现**方向完全相反**。实测：时点 +90 天后事前 545→691、事后 382→234，信息其实是**由事后迁入事前**。更值得警惕的是——**断言本身是对的，只有文字是错的**，所以测试一直是绿的；而这句错话会被直接念进演示视频 | 三处文字全部改正；`test/pit.test.js` 补上 `exPostCount` 反向断言；`test/pipeline.test.js` 新增跨 `+0/+1/+7/+30/+90` 的**单调性断言**（含端点严格不等式），把方向钉死在实现层 |
| 13 | 直接采信扶摇返回的 `report_date_ms` 作为"财报可得时点" | 抽样核对后发现 600519.SH 的 2024Q1 披露日返回 **2025-04-30**（晚了一年），而法定披露截止日是 **2024-04-30**。时点闸门**唯一的依据**就是这个字段——一旦采信，产品会声称"2024 年 5 月就能知道 2024 年一季报"，属于**提前知道未来**，比"晚知道"严重得多 | 新增 `resolveDisclosure`：按 A 股法定披露期限校验（一季报 4/30、半年报 8/31、三季报 10/31、年报次年 4/30），不通过则**降级到法定截止日**并逐条留证（真实数据下命中 36 条）。注意同批数据里也有正确的（300750.SZ 2025Q1），所以既不能整体丢弃也不能整体信任，只能逐条判 |
| 14 | 按文档给的字段名取财务指标（如 `operating_income_yoy_growth_ratio`） | 实际返回的字段是 `calculate_operating_income_yoy_growth_ratio`。**文档与实现不一致**，按文档写会全部取空 | 改为**后缀匹配**（`pickIndicator`），精确同名优先。这样对上游加前缀 / 改前缀有一定容忍度，且匹配落空时返回 `null` 而非抛错，缺口会如实进入 `meta.fieldGaps` |
| 15 | 用前复权价（`adjust=forward`）算收益 | 一是浮点残值（`1560.0777699999999`），二是前复权价会随**后续分红被追溯修改**——同一份报告在不同时间跑出来的数字不一样，违反"报告可复现" | 改用 `adjust=none`（未复权）+ `Number(close.toFixed(2))`。代价是跨除息日的持有收益未计入分红，这个口径已在 README 第 5.5 节显式披露 |
| 16 | 归因 A-2 的证据引用写成 `pitEvidence.slice(0, 8).map(e => e.series)` | 构造数据集下恰好取到 8 个不同序列（看起来正常），但真实数据下取到了**同一序列的 8 个日期**，页面上是 8 个重复的 `index:000300.SH`。**代码能跑、页面正常、但内容是错的** | 改为 `[...new Set(claims.map(c => c.series).filter(Boolean))]`——引用的是**该条归因实际用到的指标序列**，可去重、可核对；`test/pipeline.test.js` 加回归断言"证据引用不得重复" |
| 17 | 术语词典只收了"PE / PB / 估值"等词 | 决策 B 原文写的是"**市净率**只有 0.44 倍"，词典里没有"市净率"，于是这条决策依据**根本没被解析出来**，A-1「依据是否成立」判为空 | 补全词典：`市净率`、`市盈率`、`营收`、`净利润`、`毛利率`、`净资产收益率`、`资产负债率`；并把 `claims` 从"取第一个匹配点"改为"取决策时点可得的最新一期" |

### 这 17 个问题的共同点

第 1、5、6、8、11、12、13、16、17 条都属于**"代码能跑、页面正常、但结论或内容是错的"**。
这正是"AI 生成 + 人工验证"必须做的原因：**必须拿具体的数据去断言具体的输出**，而不是看到页面能打开就认为完成了。
第 13、14、15、16 条还都是**接入真实数据后才暴露**的：构造数据是我自己造的、口径统一，
真实上游的字段命名、披露日、复权口径、数据分布都会和预期不一致 ——
所以"换真实数据源"这一步本身就是一次最有效的验证。
因此测试里刻意写了对**具体数值**的断言，例如：

```js
test('主链路：当日收盘价（15:00）不得成为 14:20 决策的事前证据', () => {
  const r = buildReport(loadDataset(), 'D-2024-0311-A');
  const prevClose = r.exAnteEvidence.filter(e => e.series === 'price:600519.SH')
    .map(e => e.asOf).sort().at(-1);
  assert.ok(prevClose.startsWith('2024-03-08'), `事前最新收盘应为 2024-03-08，实际 ${prevClose}`);
});
```

## 4. 人工（候选人）需要复核的部分

以下是**建议候选人自己再确认一遍**的地方，AI 无法代替判断：

1. **偏差规则的阈值是否合理**：20 日 / 10% / 60 日高点 3% 以内、指标种类阈值 2 —— 这些是经验值，需要结合真实交易记录调。
2. **"信息不足"的口径**：目前只统计指标种类数，未考虑指标的信息含量差异（如"看估值分位"和"看龙虎榜"显然不同）。
3. **归因口径是否够用**：现在只有算术差。真实使用是否需要引入行业指数、引入持仓周期内的基准调整。
4. **`unknown` 分区的保守策略**：缺时间戳的信息一律不归因，会损失部分信息量。是否可接受取决于使用者的记录习惯。
5. **产品边界**：目前完全不做预测。若使用者期待"给个建议"，需要明确这是产品定义而非能力缺失。
6. **真实数据的映射口径**：PE / PB 是**推导值**（TTM EPS × 股价、BPS 由净资产 ÷ 近似股本反解），
   不是扶摇的原始字段；BPS 反解依赖"净利润 ÷ 基本 EPS = 股本"这一恒等式，在股本有变动时会有偏差。
   建议对照行情软件核对几个点。详见 [`docs/DATA_SOURCE.md`](DATA_SOURCE.md) 第 3 节。
7. **降级留下的痕**：上游披露日不可信时，产品用的是**法定截止日**（保守上界），不是真实披露日。
   真实披露日通常更早，因此财报类依据的"可得时点"偏晚 —— 这是刻意选择，不是 bug。

## 5. 可复现的验证方式

```bash
npm test                          # 70 个用例，含上述问题的回归断言
npm run smoke                     # 14 项前端渲染检查
npm run analyze                   # 打印三条决策的完整复盘（构造数据集）
npm run analyze -- --source real   # 同一套算法，换真实数据源（扶摇快照）
npm run analyze -- D-2024-0311-A --as-of 2024-04-01T10:00:00+08:00   # 时点闸门效果
npm run analyze:fault             # 数据缺失时的降级行为
npm run fetch:fuyao               # 从扶摇拉取真实数据并落盘（需 FUYAO_API_KEY）
npm start                         # Web 产品（页面上可切换数据源）
```

另有一项贯穿性防线：`test/fuyao.test.js` → **`数据快照与产物中不得出现任何 API Key（题目明令禁止提交密钥）`**，

这两条断言把风险挡在入库之前。
